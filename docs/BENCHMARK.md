# Performance and value benchmark (P15-E)

Generated by `script/benchmark_release` against an OFFLINE scripted model: no
provider is called, no network is touched, and the scenario is seed-free by
construction. A live-provider number would not be seed-controlled and is not
claimed.

## What is gated, and what is only reported

Wall-clock latency on a developer machine is not reproducible. Gating it would
produce a benchmark that fails for reasons unrelated to the code, and a gate
that fails for noise is a gate people learn to ignore. So:

| Class | Metrics | Behaviour |
|---|---|---|
| **Gated** | model calls per turn, durable checkpoints per turn, file-descriptor growth, thread growth | exact; a change fails the benchmark |
| Reported | p50/p95/p99 wall clock, durability overhead ratio | environment-dependent; measured and published, never gated |

## Gated counters

| Counter | Value |
|---|---:|
| `repetitions` | 20 |
| `warmup` | 3 |
| `model_calls_per_ephemeral_turn` | 3 |
| `model_calls_per_durable_turn` | 3 |
| `durable_checkpoints_per_turn` | 8 |
| `file_descriptor_growth` | 0 |
| `thread_growth` | 0 |

File-descriptor and thread growth are gated ABSOLUTELY, not merely against the
pin: a leak is a defect whatever the pin says.

## Measured latency

| Scenario | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---:|---:|---:|
| ephemeral turn | 0.1 | 0.23 | 1.32 |
| durable turn | 40.99 | 43.72 | 43.79 |

**Durability overhead: 243.89x** — and that number needs its context or
it will mislead. The ephemeral turn calls an in-process scripted model and
touches no disk, so it costs almost nothing; the ratio is therefore close to
"durable commits versus doing nothing", not "Tamoz versus another agent
framework". Against a REAL provider, a turn spends hundreds of milliseconds to
seconds waiting on the network, and the same durable overhead
(40.99ms here) is a small fraction of it.

What the number honestly says: the same scripted turn through the ephemeral
`Runtime` and the durable `Session` differs by checkpointing, the request inbox,
the lease and the effect journal, and nothing else — and that costs roughly
40.99ms per turn on this machine. Whether that
is worth surviving `kill -9` is the reader's call, but it is the real price.

Measured on Ruby 3.3.11 / arm64-darwin25 at
2026-08-06T07:07:59Z. Latency numbers from a
different machine are expected to differ and are not a regression.

## Not attempted

- plain RubyLLM script comparison
- external job-queue comparison
- live-provider latency (not seed-controlled; would not be reproducible)

A synthetic race against a plain RubyLLM script or an external job queue would
measure the harness rather than the systems: they are different products with
different guarantees. Claiming such a number would be worse than omitting it.
