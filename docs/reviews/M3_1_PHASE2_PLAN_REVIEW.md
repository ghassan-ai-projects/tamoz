# M3.1 phase 2 plan review

Review target: [M3_1_PHASE2_PLAN.md](../M3_1_PHASE2_PLAN.md)

Decision: accepted for implementation after the corrections recorded below.

## Review method

The review mapped every transaction and statement hook currently reachable from
`checkpoint_store.rb` and `lease_operations.rb`, then challenged the proposed proof from
five directions:

1. missing instrumentation hidden by traces;
2. a child falsely attesting to its own kill point;
3. correlated production readers accepting correlated writer defects;
4. unbounded dynamic labels, retries, loops, scenarios, or shards;
5. ambiguous attribution between timeout, intentional kill, cleanup, and external state.

It also checked the plan against the committed M3.1 scope and the user's phase discipline.
No phase 2 code may begin before this review and plan are committed.

Process amendment on 2026-07-30: the user replaced the original atomic phase-commit rule
with independently reviewed slice commits. Each slice must pass full CI and record its own
review before the next begins; Phase 2 still ends with a cross-slice review.

Post-acceptance correction on 2026-07-31: source inventory before Phase 2E found that the
fixed matrix had no witness for `request.claim.active_execution`. Phase 2E stopped before
code changes. The Five Whys, added `request.claim-resume` scenario, and strengthened
statement-to-scenario witness gate are recorded in
[M3_1_PHASE2E_PLAN_CORRECTION.md](M3_1_PHASE2E_PLAN_CORRECTION.md).

## Findings resolved

| Severity | Finding | Root cause | Resolution |
|---|---|---|---|
| Critical | Phase 1 process semantics made every harness kill imply timeout. | Timeout was the only intentional termination use case implemented. | Add `termination_reason`; selector kills are non-timeout parent interventions and have distinct schema relations. |
| Critical | A runtime trace cannot reveal a missing hook. | Reachability was being treated as boundary completeness. | Add a versioned registry plus independent Ripper source audit; compare source, registry, and trace as three separate sets. |
| Critical | The existing child self-kill cannot prove that a parent observed the requested selector. | Subject execution and evidence authority were the same process. | Child fsyncs exact control and stops; parent validates control and alone sends group `SIGKILL`. |
| Critical | Reopening through Tamoz could repeat the writer's logical defect. | Recovery behavior was conflated with atomicity classification. | Classify with a standalone raw-SQL oracle that cannot load Tamoz; run Tamoz recovery only after classification. |
| Critical | Expected “new” state generated by running the same production transition would be a correlated oracle. | Reference execution was mistaken for reference semantics. | Hand-author relational old/new contracts; never construct expected state with the operation under test. |
| High | One process record cannot describe intentional intervention without contradictory timeout fields. | Termination action and reason were not modeled separately. | Bind termination action, reason, signal, and timeout with relational verifier checks. |
| High | The child could write control and continue past the hook before the parent kills it. | File polling alone is not a suspension barrier. | Child sends itself `SIGSTOP` immediately after close/fsync; callback cannot return. |
| High | The plan initially trusted that `SIGSTOP` happened without observing it. | Control persistence and process suspension were treated as one event. | Parent must observe `WUNTRACED` stop status and exact `SIGSTOP` before accepting control or killing. |
| High | Dynamic statement labels could make the selector set unbounded. | Concrete loop indices and semantic boundaries were conflated. | Permit only reviewed templates, bound fixture counts, and collapse repeated coverage into fixed iteration classes. |
| High | Registering only observed phase 2 paths could hide deferred operations in the same files. | Phase scope and registry scope were conflated. | Register deferred operations with phase ownership and `kill_required: false`; prohibit a global completeness claim. |
| High | Duplicate request and pending-write paths need different expected outcomes despite sharing operation labels. | SQL coverage and scenario semantics were conflated. | Keep scenario identity in every selector and provide separate old/new/stable contracts for idempotent branches. |
| High | Idempotent duplicate and read-only scenarios have byte-identical old/new states. | A two-class oracle assumed every commit mutates. | Add an explicit `stable` class declared only by the scenario contract; never infer it opportunistically. |
| High | A release matrix could be “green” with missing shards or mixed revisions. | Individual shard success did not prove union completeness. | Merge verifies disjoint/full selector set and identical subject, registry, recorder, and scenario digests. |
| High | Generated UUIDs/timestamps make byte-for-byte new-state fixtures unstable. | Physical representation was confused with logical state. | Oracle validates relational roles, counters, digests, and invariants while omitting generated raw values. |
| High | Hook metadata currently lacks attempt on statement events. | `Transaction` does not receive the kernel attempt. | Propagate nullable attempt and emit a fixed versioned metadata schema on every hook. |
| Medium | Read-only transactional paths could be silently omitted. | “Crash safety” was interpreted as writes only. | Registry includes read-only boundaries and scenario coverage, while kill requirements remain explicitly classified. |
| Medium | Busy/retry selectors could be claimed without a real locked-writer trace. | The selector model supported retries before the treatment existed. | Phase 2 records first attempts only and names retry/exhausted evidence as phase 5 work. |
| Medium | A generic oracle accepting arbitrary SQL would become an execution surface. | Flexibility was prioritized over containment. | Standalone oracle accepts only fixed scenario ids and a database path; all SQL is source-controlled. |
| Medium | Control artifacts could leak database paths or process ids. | Diagnostic convenience was not bounded by content policy. | Control contains public semantic labels/digests only; paths and operating-system identities remain parent-local. |
| Medium | A successful sibling call marker could tear under process death. | A convenient append-only file was being treated as durable truth. | Use a separate `synchronous=FULL` SQLite call ledger with an invocation uniqueness constraint. |

## Five Whys: child self-attestation

1. Why does a self-killed child not prove selector coverage? It cannot report after death.
2. Why is observing `SIGKILL` insufficient? The child may have died elsewhere or before the
   requested hook.
3. Why is a pre-kill file alone insufficient? The child could continue and cross another
   durability boundary while the parent polls.
4. Why use `SIGSTOP`? It is an OS-enforced barrier after the fsynced record and before the
   callback returns.
5. Why is the parent authoritative? It observes the exact stopped status, validates
   control, sends `SIGKILL`, reaps the process group, and records all facts independently.

## Five Whys: correlated new-state oracle

1. Why not run the same operation on a clone and compare? Both executions can reproduce the
   same bug.
2. Why not compare Tamoz objects? The materializer can share the writer's assumptions.
3. Why are generated UUIDs a complication? Correct new states are not byte-identical across
   independent executions.
4. Why use relational contracts? They describe required rows, counters, identities,
   digests, ordering, and references without depending on generated concrete values.
5. Why run recovery afterward? Atomicity and public convergence are different claims and
   need different evidence.

## Five Whys: trace completeness

1. Why can every observed hook pass while coverage is incomplete? Missing hooks emit
   nothing.
2. Why is a handwritten registry not enough? It can omit the same source boundary.
3. Why is source extraction not enough? It cannot prove a branch is reachable under the
   fixed scenarios.
4. Why use three sets? Source audit detects code boundaries, registry assigns reviewed
   meaning/ownership, and traces prove scenario reachability.
5. Why retain deferred entries? They expose the remaining work and prevent a local phase
   claim from becoming a global persistence claim.

## Acceptance conditions

Implementation may begin because:

- the phase has an exact capability and non-claim boundary;
- source, registry, and runtime reachability have independent gates;
- intentional kill is modeled separately from timeout;
- the control protocol prevents child progress and child self-attestation;
- expected state is independently specified;
- every scenario, selector, process, shard, artifact, and deadline is bounded;
- phase 5 retry evidence and phase 3/4 capabilities remain visible and unclaimed;
- every implementation slice requires deep review, complete CI, and its own commit;
- phase completion additionally requires a final cross-slice review.

Implementation stops and this plan is revised if:

- `SIGSTOP` cannot be made reliable on a supported release platform;
- the Ripper audit cannot reject arbitrary label interpolation;
- a scenario requires the production reader to classify old/new/stable state;
- selector count cannot be bounded by reviewed fixtures;
- phase 1 subprocess cleanup cannot safely support parent intervention.

## Residual limits

- Phase 2 targets POSIX process groups/signals. Unsupported platforms must skip explicitly
  and cannot provide release crash evidence.
- Local execution can prove Ruby 3.3.11 only; Ruby 3.4/4.0 remain exact-revision CI gates.
- Full release-matrix wall time will be measured during implementation and may require
  deterministic sharding; reducing selector coverage is not an accepted optimization.
- Artifacts remain internal until phase 7 sanitization and public-case packaging.
