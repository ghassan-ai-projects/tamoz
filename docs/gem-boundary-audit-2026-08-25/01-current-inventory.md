## Package-truth observations

`tamoz-evals`'s OpenClaw comms fixture directly requires `tamoz/comms` and
`tamoz/telegram` at
[`openclaw_comms_fixture.rb`](../../test/support/openclaw_comms_fixture.rb:9-12),
but the current evals gemspec does not declare either dependency. The shared
monorepo bundle masks this. A runner split would give those imports an honest
owner; the verifier gem should not absorb them.

The public architecture page still says “seventeen independently publishable
gems” and omits the focused agent gems. That is documentation drift, not proof
that the current source topology is wrong, but it is a release-quality follow-up
before publishing a new gem.

The root README and `docs/P3_AGENT_SCORECARD.md` also describe ordinary eval
loading as stdlib-only, while `tamoz/evals.rb` eagerly requires the runtime
surface. Separately, several public data-model pages still cite SQLite migration
version 13 while the source migrator is at version 21. These are documentation
follow-ups discovered during the scan, not silently corrected here.

consumer payoffs as the decision evidence.

## Package-truth defects that affect extraction order

The inventory also found direct imports that are currently satisfied only by the
monorepo bundle. They are not all new-gem candidates, but they are migration
constraints:

- `tamoz-evals` directly uses `tamoz-agent-cli`, `tamoz-comms`,
  `tamoz-telegram`, and `tamoz-tools` without declaring all of them. The
  runner split must own those dependencies.
- `tamoz-agent-cli` directly loads SQLite and Telegram, while its gemspec does
  not declare both. Treat Telegram as an optional adapter; make the SQLite
  command path explicit before claiming package isolation.
- `tamoz-sqlite` directly uses Core but reaches it transitively. Its gemspec
  should eventually declare `tamoz-core` directly.
- `tamoz-agent-memory` declares SQLite and constructs `Tamoz::SQLite` stores
  without loading SQLite from its own umbrella. This is a composition-root
  dependency, not evidence for splitting the memory gem.
- `tamoz-agent` uses Scheduler constants through SQLite without declaring
  Scheduler directly. The worker composition root should own that edge.
- `tamoz-scheduler` contains `ScorecardSummaryConsumer` and `ScorecardResult`,
  which execute eval-specific work. Move those into the eval runner or replace
  them with an injected consumer protocol; never add a scheduler-to-evals
  dependency.

These defects are static findings only. No isolated package install or boot
probe was run.
