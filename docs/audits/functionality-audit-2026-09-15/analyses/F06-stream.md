## Behavior path

## Lens: correctness

**Proven good.** The stream contract is enforced, not assumed: sequence, single terminal, terminal-required, and the event-size bound are all in `validate_stream_event`/`assert_terminal!` (`episode_worker.rb:177-196`), and `EpisodeStream#terminal` raises on a second terminal (`episode_stream.rb:123-126`). A graph node cannot forge a model event — `EpisodeStreamAdapter#emit` raises `StreamError` for `model_started`/`model_delta`/`model_completed` (`episode_stream.rb:191-196`); the only crossing is `emit_stream_part` fed by journal-verified receipts (`:208-213`, `situation_request.rb:898-917`). Receipt verification is genuinely triple-bound: `response_digest`, `request_digest` and `provider_configuration_digest` must all equal the journaled succeeded attempt's (`situation_request.rb:921-934`), and forged provider markers are refused (`:936-946`). The snapshot identity cross-check (`:448-455`) is the correct direction — the digest-verified document wins over the wire header. `request_id` ambiguity via `.` in ids is actively refused (`:207-220`), and I confirmed the guard fires: probe `f06_dup_probe2.rb` shows `("ep.1","a")`, `("ep","1.a")`, `("ep.1.a","b")` all refused while `("ep","1")` is accepted with `request_id="episode.ep.1.1"`.

**Correctness defects found (all four are the same family — an unvalidated wire value crossing a typed boundary).**

- `EpisodeStreamAdapter#typed_code` (`episode_stream.rb:258-269`) resolves the graph's `error_class` string with `const_get(part, false)` and then calls `klass.const_defined?(:CATEGORY, false)`. Probe `f06_typedcode3.rb` against the real adapter: `"Tamoz::Stream::BudgetExceededError" → "stream_budget_exceeded"` (correct), `"Tamoz::Core::ToolError" → "graph_step_failed"` (correct). The failure mode needs a `Tamoz::`-prefixed constant that is **not** a Module: only `NoMethodError`/`TypeError` escape — `NameError` is caught (`:267-268`), which is why the obvious `Tamoz::NoSuchThing` case is safe. Recorded as F06-COR-01, minor, medium.
- `EpisodeRunner#run`'s `rescue` (`situation_request.rb:404-408`) covers `fail_stream` but `stream.events.each` sits **after** the `end` (`:409`), outside it. If the stream cannot be built or terminalised, the exception escapes the enumerator and gRPC returns `UNKNOWN` with no stream contract at all. Probe `f06_failpath_probe.rb` reproduces the escape in the exact plumbing shape. Recorded as F06-REL-01, minor, medium.
- `validate_tool_request!` (`episode_nodes.rb:602-613`, `tamoz-agent-kernel`, reached from this row's wire) does `Array(parsed).map { |entry| entry.fetch("name", nil) }` with no shape guard. Probe `f06_toolcatalog_probe.rb`: `"\"just a string\""` → `NoMethodError: undefined method 'fetch' for an instance of String`; `"42"` → the same for Integer. The caller's own contract is `ProtocolError` (`episode_nodes.rb:607`). Recorded as F06-COR-02, minor, high.
- Three wire strings become graph instructions with no digest: `prompt` (`situation_request.rb:337` → `episode_nodes.rb:323` → `episode_frame_builder.rb:52,100`), `objective` (→ `:320` → `:101`), `execution_id`/`run_id` (`:481-483`). `prompt_sha256` and `objective_sha256` are carried and **only** cross-checked inside `verify_manifest_digest!` (`:718-726, 754-769`), which runs solely when an `ArtifactStore` is bound (`:529`) and *after* the model call. I measured the assembled trusted section with the real builder (`f06_watch_probe.rb`): the model's system message is literally `SYS PROMPT` + `OBJECTIVE: obj` + the operator diagnosis catalog + the framing lines. Recorded as F06-SEC-01, major, high.

**Not evidenced.** No runtime proof that a `NoMethodError`/`TypeError` actually escapes `typed_code` from a real graph error event; the class of names that reaches it is unverified (see Blind spots).

## Lens: security and authority

**Admission point, named exactly.** External bytes become graph/model input at `EpisodeRunner#admit_request` (`situation_request.rb:438-446`) and nowhere earlier: `EpisodeWorker#validate_request!` (`episode_worker.rb:127-151`) is a gate, not a projection, and the runner is the only thing that turns a `wire_request` into `envelope.payload` (`:152-160`) and a `Context` (`:478-492`).

**What is treated as untrusted DATA, correctly.** The snapshot is verified before use (`:440-442`) and its facts reach the model only inside the fenced, attributed user section (`episode_frame_builder.rb:116-136`, each fact as `{"id" => "fact:<name>", "value" => ...}`), never as prompt text. Recalled memory is fenced the same way (`:148-155`). The capability host is constructed from an explicit map, refuses unknown keys, and hands implementations a frozen seven-key context view with no effects/store/emitter/`graph_runtime` (`capability_host.rb:40-42, 122-133, 157-167`); `descriptors` is fixed and model-visible (`:73-82`), and the seven-name surface is asserted by `test/stream_episode_capability_host_test.rb:41-56` (9 runs / 441 assertions, 0F). The reasoning document's `evidence_refs` are grounded against the frame's own ids (`episode_nodes.rb:653-662`). A stream payload therefore **cannot** widen the tool surface, the file/secret surface, or the process surface from this gem.

**Egress is the one field that is not narrowed.** `evidence_tools_endpoint` is admitted with no validation of any kind (`situation_request.rb:320`, `:804-810`) and dialled verbatim (`evidence_client.rb:127-132`), with the capability token attached (`:159`). The stated trust boundary is "UDS + mTLS in production" (`worker_server.rb:17-19`, `evidence_client.rb:122-124`) but the gRPC target is `:this_channel_is_insecure` and scheme-agnostic — `unix://`, `dns://`, `ipv4:`, `http://`, or a bare `host:port` all dial. This does **not** widen anything a request-scoped payload controls (the endpoint and token ride the same request), so it is recorded as `info` (F06-SEC-02), not as a bypass.

**Untrusted content as INSTRUCTION — the row's real security finding.** The `prompt` and `objective` strings are emitted into the **trusted policy section** of the model frame (`episode_frame_builder.rb:52,100-101`) with no digest gate on the path that runs. `prompt_digest`/`verify_prompt!` (`:37-46, 70-75`) compares the prompt against the wire's *own* `prompt_sha256`; a peer that supplies both the bytes and the digest of the bytes always passes, so it binds transport integrity, not authority. The only independent check is `verify_manifest_digest!` — and its `case` (`situation_request.rb:755-763`) **returns early for `"prompt"` and `"diagnosis_catalog"`**; those two are only ever verified against their own wire digests. So a peer controlling the gRPC request controls the model's system instructions, its objective, its `run_id`, and its diagnosis code descriptions with no cross-boundary check at all. That is a genuine "external stream content treated as instruction" result at the exact admission point this row owns — F06-SEC-01.

**Reverse channel authority.** Nothing pushed back to the stream peer carries authority: the `EvidenceToolCall` fields are identity echoes, bound caps, and the opaque token (`evidence_client.rb:152-174`); the token is never verified here by design (`:12-15`) and never persisted (`situation_request.rb:147-151`, confirmed by the payload construction at `:309-351`, which omits it). The result is verified before use — identity (`:208-212`), attempt/fence echo required on data results (`:214-218`), UTF-8 (`:231-242`), a mandatory digest (`:244-249`), and `verify_digest` under the shared `situation-runtime/evidence/v1` domain (`:220-229`). **The reverse channel cannot carry approvals or commands:** the `EvidenceTools` service in the pinned proto has exactly one unary RPC (`contracts/runtime-v1.proto:25-27`), and there is no approval or command message in the whole schema. Approvals travel the other direction, on Channel B/C — the subscriber's CloudEvents feed and the `ApprovalRelay#submit_decision` port (`approval_relay.rb:119-130`), where the relay asserts *who* answered and is forbidden from being the approver (`:176-181`), the nonce is single-use (`:193-198`), and the assertion binds eleven fields under `situation-runtime/approval-assertion/v1` (`:200-225`).

**Learning loop, from this boundary.** `outcome.reconciled` → `LiveLearningHandlers#reconcile_outcome` (`live_learning_handlers.rb:61-78`) → `admit_learnable_episode` (`:80-86`) → `@memory.admission.admit_episode(episode:, owner: "stream", reconciled_outcome:, verify_source_authority: ...)` (`:88-96`). The write is `layer: :experience, klass: :episode, state: :candidate` (`admission.rb:335-337`) and the statement is built from the episode's grounded parts, never a transcript (`:326-331`). What reaches it is the `episode_content_for` hash built by the runner (`situation_request.rb:611-632`) — bounded fields plus `scopes`. **Promotion to `:active` is automatic, not human-gated:** `Admission#admit` (`admission.rb:242-268`) checks duplicate identity, then `reject_reason` (`:286-302`: size, secret-shaped, speculation-as-fact, missing provenance, recalled-as-new, unknown scope, and the rest), then appends the record `state: :active`. The reader-side boundary is real and tenanted — `MemoryStore#search` filters `scopes_tenant`/`scopes_user`/`scopes_project`/sensitivity/compatibility and, for a situation caller, `scopes_situation_type`/`scopes_entity_type` (`memory_store.rb:410-430, 633-642`) — and the learner consumes `:observed`-only records with verified provenance (`situation_recaller.rb:129-149`). The *situation* dimension is the weak one: `situation_boundary` (`:633-642`) matches `situation_type` + `entity_type` but **not** `scopes_entity_id`, and the deletion of cross-entity neighbours happens back in Ruby (`situation_recaller.rb:92`), so a cross-**situation** neighbour survives every filter; and `Tamoz::Core::SituationRecall.validate!` (`situation_recall.rb:87-93`) checks only that the argument is a `Result` — it is not the crossing validator its call site appears to assume (`situation_memory.rb:13`). Recorded as F06-SEC-03, major, medium.

**Verified non-issues.** The `.`-ambiguous request id is refused (`:207-220`). `allowed_intent_types` is bounded to 16 (`:237-242`) and is the authority list — the model's own risk claim is never read (`decision_builder.rb:288-290`, `:131-143`), and a ceiling below the catalog-declared risk demotes to the watch condition rather than escalating (`:207-209`). Watch confidence can only cause abstention (`:184-189`).

## Lens: reliability and durability

**Supervision on a mid-episode connection drop — the answer is "lost from this worker's side; the durable request survives".** The execute enumerator is the RPC body. On a client disconnect gRPC calls `call.cancelled?`, the watcher (`:863-875`) cancels the context token, the graph aborts at its next check leaving a resumable checkpoint, and the terminal is written to a closed stream, i.e. dropped — the comments say so (`:860-862`) and the token's own `cancel!` semantics (`gems/tamoz-cancellation/lib/tamoz/cancellation_token.rb:53-74`) do not kill the thread. What is **not** lost is the durable request: the episode is enqueued under the fenced `request_id` (`:498-506`), so a `fence+1` redispatch is a new request that reuses completed receipts, and a redelivered same-fence attempt is idempotent on the same id. I did **not** find any path by which the worker itself resumes a dropped episode: `recover` (`gems/tamoz-graph/lib/tamoz/graph/durable_runner.rb:101-153`) is never called from `tamoz-stream` (`EpisodeRunner#run` calls only `deliver`). Durability is real, resumption is the peer's job, and the split is stated (`situation_request.rb:370-375`).

**Durability across a worker restart.** The checkpointer is the SQLite adapter (`bin/tamoz-stream-worker:86-88`), the request inbox is the same durable store, and `test/stream_episode_crash_matrix_test.rb` proves the two interesting cases (2 runs / 18 assertions / 0F): a `fence+1` redispatch reuses the completed receipt with **no second provider call**, and a started-without-receipt attempt is a typed `unknown` with no blind retry. The runner's own artifacts are external state: `ArtifactStore` is in-memory (`artifact_store.rb:26-31`) and is reconstructed on every boot (`bin/tamoz-stream-worker:132`), so a PRODUCED terminal's manifest names digests that no longer resolve after a restart. That is the store's documented scope ("Eviction policy is the deployment's", `:14-16`) but the production composition binds no durable implementation, so the manifest→artifact contract is not durable in the shipped launcher. `info` (F06-REL-03).

**Can the same episode run twice concurrently? No — and it is guarded twice.** gRPC dispatches each RPC on its own pool thread (`worker_server.rb:37`, `pool_size: 16` default), so two concurrent `Execute` calls for the same `(episode_id, attempt_id, fence)` do reach the runner. They do **not** run the graph twice: `DurableRunner#deliver` queues, then `run_next` opens a writer (`durable_runner.rb:186-205, 71-100`), and the SQLite lease acquisition refuses a second writer on the same `(thread_id, namespace)` while an unexpired lease is held — `CheckpointConflictError, "thread namespace already has an unexpired lease"` (`gems/tamoz-sqlite/lib/tamoz/sqlite/lease_operations.rb:51-54`). `enqueue_request` is idempotent on `request_id` (`durable_runner.rb:32-45`; the crash matrix proves reuse). **Caveat, recorded as a lead not a finding:** the resulting `CheckpointConflictError` is caught by the generic `rescue StandardError` (`:404`), so the second client sees `TERMINAL_STATUS_FAILED` with `reason_code == "stream"` (`errors.rb:8-12` → `wire_code_for` at `:432-436`) rather than a retryable refusal — an observability cost only, since the durable state is correct.

**Partial/failed evidence pull.** Bounded and typed: unary call with the episode deadline as a gRPC deadline (`evidence_client.rb:185-191`) or a typed refusal if it is already past (`:320-329`), cancellation checked before and after (`:302-311`), and every transport failure collapsed into a typed `EvidenceError` (`:89-95`) that the capability host passes through rather than re-wrapping (`capability_host.rb:96-97`). A host refusal is turned into a typed error with the code sanitized (`evidence_client.rb:176-183`). **The truncation flag is dropped after verification:** `build_result_hash` returns `"truncated" => result.truncated` and `"row_count"` (`:251-258`), but `EpisodeToolCall` journals only a projection and `build_tool_entries` (`episode_frame_builder.rb:157-168`) renders only `is_error`, `result_bytes`, `result_sha256`, `request_sha256`. So the model cannot tell a complete result from a truncated one while the wire carried the fact. `info` (F06-REL-02).

**Cancellation.** Real but unobservable: the watcher (`:863-875`) polls at 0.1 s and `EpisodeStream#cancelling` (`episode_stream.rb:111-117`) exists in the vocabulary but is **never called** anywhere in the gem, so a cancelled episode reaches the client only through the terminal. `test/stream_episode_crash_matrix_test.rb` and `test/stream_invariants_test.rb` contain no cancellation case (grepped: zero hits for "cancel" in both; the single `cancel_product_transfer` hit at `stream_invariants_test.rb:244` is an intent type). Recorded as a coverage gap under F06-REL-01's observation, not as a separate finding.

## Lens: observability and evidence

**Proven good.** The evidence chain is attributable end to end: journal-verified receipts are the only source of model events (`situation_request.rb:886-917`), each event carries `(episode_id, attempt_id, fence)` on **every** frame (`episode_stream.rb:138-150`), the terminal carries the artifact manifest with the prompt/skill-set/tool-catalog/memory-digest identity (`:667-681`), and `wire_refused_model_event/...` categories (`:932, 940, 944`) name refusals exactly. Trace context is validated and bounded (`:273-280`: W3C pattern, 512-byte tracestate) and forwarded to both the context (`:853-858`) and the evidence call (`:163-164`). Terminal reason codes come from the durable request's typed error (`:568-575`). Every stream error carries `CATEGORY` and a `SAFE_MESSAGE` (`errors.rb:8-47`) and the capability host discloses only the wrapped class, never an adapter message (`capability_host.rb:98-103`).

**Gaps.** (1) `EpisodeStream#cancelling` is dead vocabulary — a consumer cannot distinguish "cancelled" from "the stream just stopped" except by the terminal, and an RPC that dies before the terminal gives the client nothing. ### F06-SEC-01 — `prompt` and `objective` reach the model as instructions with no authority check; the one digest verifier is unreachable for them

- **Severity / confidence / status:** major / high / open.
- **Source evidence:** `gems/tamoz-stream/lib/tamoz/stream/situation_request.rb:337` (`"prompt" => @wire.prompt.to_s`) and `:346` (`"objective" => @wire.objective.to_s`); `:332-350` (the whole `wire_payload` — none of it validated by `EpisodeRequestEnvelope#validate!` at `:169-183`); `:478-492` (`build_context`, where `execution_id`/`run_id` become `envelope.request_id` and not `@wire.execution_id`); `:495-506` (`execute_turn` passes `envelope.payload` to the durable runner); `gems/tamoz-agent-kernel/lib/tamoz/agent/episode_nodes.rb:320-325` (`wire.fetch("objective", "")`, `wire.fetch("prompt", "")`, `wire.fetch("prompt_version", "")` into the frame builder); `gems/tamoz-agent-kernel/lib/tamoz/agent/episode_frame_builder.rb:52` and `:99-101` (`build_system(prompt)` — the **trusted policy section**); `episode_frame_builder.rb:37-46, 70-75` (`verify_prompt!` against the wire's own digest — transport integrity only); `situation_request.rb:718-726` and `:754-769` (`verify_manifest_digest!` returns early for `"prompt"` and `"diagnosis_catalog"`); `situation_request.rb:529` (`retain_manifest_artifacts` runs only when `@artifact_store` is bound).
- **Test/contract evidence:** no test asserts any bound on `prompt` bytes or any cross-check of `prompt_sha256` against a spec-bound digest. Probe `f06_watch_probe.rb` (real `EpisodeFrameBuilder`) prints the assembled system message: `SYS PROMPT` + `OBJECTIVE: obj` + catalog lines. `not found` for a negative test.
- **Scanner signal:** none — found by tracing `wire_payload` → `build_frame` → `build_system`.
- **Independent judgment:** confirmed that no validation, digest cross-check, length bound, or framing separates these strings from the operator block; rejected the reading that `verify_prompt!` provides the missing authority (it compares the prompt with the digest the same peer sent). I could **not** establish which production intermediary signs or constrains the request, so the exploitability claim is bounded to "a peer that can craft the request".
- **Root cause (five whys):** (1) Why can a request redefine the model's system instructions? Because `prompt` is emitted verbatim into the trusted section. (2) Why is it emitted verbatim? `EpisodeFrameBuilder` treats `prompt` as operator-authored by contract (`episode_frame_builder.rb:11-13`) and has no way to know its provenance. (3) Why does nothing upstream establish that provenance? `EpisodeRequestEnvelope` validates identity, kind, lane, risk, intent catalog, budget and trace context (`situation_request.rb:169-183`) but never the prompt/objective, and `verify_manifest_digest!` explicitly skips them (`:762-763`). (4) Why does that gap survive? The worker's stated design is that the capability token is "OPAQUE — the stream's EvidenceTools verifies it" (`:37-39`) and the wire is the trust boundary (`worker_server.rb:17-19`), so the worker was built to trust the request rather than to authenticate it. (5) Why is that insufficient? The containment work (`capability_host.rb`) narrowed what the model can *do* but the instruction channel was never narrowed, so a peer that controls the request controls the instructions. The contract that would prevent recurrence: **every field entering the trusted frame section must carry a digest verified against an authority the worker already holds** — the intent catalog already has exactly this gate (`IntentCatalog.verify_wire`), and the prompt/objective do not.
- **Recommendation:** the smallest credible action at the existing seam — extend `verify_manifest_digest!`'s `case` (`situation_request.rb:754-769`) with the two documents it currently skips, or move the prompt/objective verification out of the `@artifact_store`-conditional path (`:529`) so it runs before `execute_turn`. Do **not** add a class or a new digest domain: `IntentCatalog.verify_wire` is the existing pattern, and the wire already carries `prompt_sha256`/`objective_sha256`.
- **Disposition:** open; needs independent challenge on exploitability (see coordinator flags).

### F06-SEC-03 — situation recall spans different situations, and the divergence survives to promotion

- **Severity / confidence / status:** major / medium / open.
- **Source evidence:** `gems/tamoz-sqlite/lib/tamoz/sqlite/memory_store.rb:633-642` (`situation_boundary` filters `scopes_situation_type` + `scopes_entity_type`, **not** `scopes_entity_id`); `:410-430` (`authorized_scan_body` applies it to the main candidate scan); `gems/tamoz-agent-memory/lib/tamoz/agent/memory/situation_recaller.rb:92` (`next if row.fetch("scopes_entity_id") == current_entity_id` — the *only* entity-id exclusion, applied in Ruby, after the SQL shortlist and before the 64/32 KiB bounds at `:108-112`); `gems/tamoz-agent-memory/lib/tamoz/agent/memory/situation_recaller.rb:35` (`limit: [normalized_limit * 8, 512].min`) vs `:37-44` (`build_result(..., normalized_limit)`); `gems/tamoz-agent-memory/lib/tamoz/agent/memory/situation_recaller.rb:146-163` (`projection` copies `situation_type` into `scopes`); `gems/tamoz-core/lib/tamoz/core/situation_recall.rb:28-33` (`validate_fields!` — only key-set and non-empty String); `:87-93` (`validate!` — only `is_a?(Result)`); `gems/tamoz-stream/lib/tamoz/stream/situation_memory.rb:12-16` (the wrapper whose name implies a crossing check); `gems/tamoz-agent-memory/lib/tamoz/agent/memory/admission.rb:242-268` (`admit` → `state: :active` automatically); `gems/tamoz-stream/lib/tamoz/stream/live_learning_handlers.rb:88-96` (how an episode reaches that admission).
- **Test/contract evidence:** `test/stream_learning_loop_test.rb:477-522` — `test_a_related_entity_retrieves_the_first_occurrence_within_the_boundary` (same `situation_type: "equipment"`, different `entity_id` → the related neighbour is retrieved) and `test_out_of_boundary_entities_retrieve_nothing` (a different **`entity_type`** → empty). The existing tests use one entity type per situation type, so they cannot distinguish "entity_type" from "situation_type + entity_type". Command: `ruby -Itest test/stream_learning_loop_test.rb` → 17 runs / 84 assertions / 0F. Probe `f06_recall_probe2.rb`: a projection whose `situation_type` is `"greenhouse"` passes `Tamoz::Core::SituationRecall.validate!` unchanged.
- **Scanner signal:** grep for `situation_boundary` after reading the F06 boundary question "what reaches the model from an external stream".
- **Independent judgment:** confirmed the SQL boundary omits `entity_id` and that the Ruby exclusion runs after it; confirmed `validate!` has no scope check; confirmed that a self-describing digest would close this, because `Projection#digest` is `record.digest` (`situation_recaller.rb:163`) and `MemoryRecordDigest.identity(statement)` (`admission.rb:333`) does not cover the scopes — probe `f06_recall_flip2.rb` shows the same statement/provenance accepted with two entirely different digests, so `record_digests == projections.map(&:digest)` (`situation_recall.rb:64-67`) proves nothing about content. Could **not** establish a production pairing where one tenant has two `situation_type`s sharing an `entity_type` — the five fixture domains use distinct pairs (`aquaculture`/`pond`, `greenhouse`/`greenhouse_zone`, `cold-chain`, `logistics`, `thermal-lab`). The property therefore rests on the value shapes being independent, which the code arranges deliberately (`situation_request.rb:611-632` sets `situation_type` from the snapshot and `entity_type` from the entity).
- **Root cause (five whys):** (1) Why can a climate episode receive an aquaculture episode's statement? Because the candidate scan matches on `situation_type` + `entity_type` and the caller's `situation_type` is the *current* episode's. (2) Why does the filter exist at all if it is wrong? Because `MemoryStore#situation_boundary` implements "same tenant AND same entity type" (its own comment, `:626-632`) — an entity-level rule. (3) Why is the situation dimension the one the recaller needs? Because `SituationRecaller` binds `situation_type`/`entity_type`/`entity_id` into the caller (`:69-76`) and treats `situation_type` as part of the boundary (`:39-41`). (4) Why did the mismatch survive? The two halves live in different gems (`tamoz-sqlite` owns the SQL, `tamoz-agent-memory` owns the recaller) and their shared contract (`tamoz-core`'s `SituationRecall`) validates shape, not semantics. (5) Why does shape validation not catch it? Because `validate_fields!` checks the key set and the value types, never the values' relationship or their agreement with the digest. The contract that would prevent recurrence: **the recall boundary must be enforced where the boundary is declared, and the projection digest must bind the scoped content** so a consumer can reject a record that lies about its provenance.
- **Recommendation:** two one-line changes at existing seams — add `AND i.scopes_entity_id <> ?` to `situation_boundary` (`memory_store.rb:633-642`, using the caller's `entity_id`, which `situation_caller` already supplies at `situation_recaller.rb:69-76`), and make `Projection#initialize` recompute-or-verify `digest` over `{statement, scopes, provenance}` (`situation_recall.rb:28-33`). No new class, no new table.
- **Disposition:** open; contract decision required (which dimension is the authority — entity type or situation type) before the fix direction is chosen.
