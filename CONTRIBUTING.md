# Contributing

Thank you for contributing to Tamoz. Tamoz is pre-release software, and the
contribution bar is deliberately explicit: the safety and durability properties
this project promises are only as strong as their tests and evidence.

## Scope

All of these are welcome:

- bug fixes, with a failing test that demonstrates the bug;
- documentation improvements to the public documentation set;
- tests that close a gap in existing behavior;
- features — after discussion. Open an issue or start a thread first; features
  are reviewed for scope and for whether they weaken a design invariant.

## Before you start

- Read [README.md](README.md) and [documentation/README.md](documentation/README.md).
- If you are contributing agent behavior, read [AGENTS.md](AGENTS.md).
- Behavioral changes must preserve the contracts in `docs/design-v0.1` — that
  package is authoritative over individual code changes.

## Development setup

From a fresh checkout:

```sh
rbenv exec bundle install
rbenv exec bundle exec rake ci
```

`rake ci` is the everyday gate: design validation, a syntax pass, the fast test
set, the gRPC proto drift check, and the architecture check.

```sh
rbenv exec bundle exec rake ci_full
```

`rake ci_full` is the complete gate — nothing skipped. It is required for
changes touching durability, MCP, packaging, or committed evidence artifacts;
`rake ci` alone warns that it skips the slow set.

## Contribution rules

1. **Preserve the documented contracts.** `docs/design-v0.1` is authoritative;
   a change that breaks a documented invariant must change the contract first,
   with review.
2. **Keep changes scoped.** One problem per pull request; say what a change does
   not do as clearly as what it does.
3. **Add tests for behavior changes, and evaluation evidence for behavioral
   changes.** Correctness and safety gates cannot be traded for a higher
   aggregate score.
4. **New runtime dependencies require an architecture decision (ADR)** and must
   pass the clean-process dependency test.
5. **Never rewrite old migrations — add new ones.** Migration ordinals are
   consumed monotonically and checksummed; existing rows are not carried forward.

## Quality gate

Every pull request must pass:

- `rake ci` — the everyday gate (above);
- `rake docs:check` — the documentation tree: links and index coverage;
- the quality ratchets under `rake quality:*` — Reek against the committed
  baseline, the SimpleCov line/branch floor, and the Enola architecture check;
- CI on Ruby 3.3, 3.4, and 4.0.

Changes touching durability, MCP, packaging, or committed evidence artifacts
additionally require `rake ci_full`. The full bar is documented in
[documentation/governance/quality.md](documentation/governance/quality.md).

## Pull request expectations

A pull request should state:

- the **problem** it solves and why;
- the **approach** taken, and rejected alternatives when they matter;
- any **contract or migration impact**;
- the **test coverage** added or changed;
- the **documentation updates** — public docs live in `documentation/`; update
  them when behavior or public contracts change.

## Documentation contributions

Public documentation lives in `documentation/` — curated, organized by topic,
and reachable from `documentation/README.md`. That is where user-facing pages
belong.

`docs/` is the internal working archive: plans, audits, reviews, and evidence.
Do not add user-facing pages there. Machine evidence artifacts in `docs/` are
regenerated by their generators and committed together with the generator.

## Generated fixtures

```sh
rbenv exec bundle exec rake fixtures:refresh
```

Commit the generator and the generated canonical artifacts together.

## Conduct

Be respectful and constructive; harassment and personal attacks are not
acceptable. See [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
