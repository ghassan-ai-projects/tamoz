# Evaluation

Tamoz ships an evidence verifier in `tamoz-evals` and an execution harness in
`tamoz-evals-runner`. The verifier turns release claims into machine-checked
evidence; the runner executes scorecards and treatments only when supplied an
explicit external input manifest.

Current version: `0.1.0.alpha.1` (pre-release).

## The three commands

The verifier is invoked as `rbenv exec bundle exec tamoz-eval` from the
checkout, or directly as `bin/tamoz-eval`:

```bash
rbenv exec bundle exec tamoz-eval verify ARTIFACT...
```

The runner commands require a `runner-input-v1` manifest:

```bash
rbenv exec bundle exec tamoz-eval-runner scorecard agent-smoke --input-manifest PATH
rbenv exec bundle exec tamoz-eval-runner treatment memory --input-manifest PATH
```

- `verify` — validates one or more release evidence artifacts (JSON documents)
  against their schemas, fail-closed on malformed, duplicate or unexpected
  content.
- `scorecard agent-smoke` — runs the deterministic agent smoke scorecard over
  the fixed case corpus and prints a report.
- `treatment memory` — runs the memory treatment-profile evaluator in
  reproducible CI mode (`mode: :ci`).

## The deterministic harness

The harness lives in `tamoz-evals-runner`. It does not package corpora,
scripted providers, deterministic MCP servers, or OpenClaw adapters; those are
caller-owned external inputs validated by the manifest.

The harness never touches a live model or network:

- **Agent smoke scorecard** (`agent_smoke_scorecard.rb`) — runs a fixed corpus
  of deterministic cases through the agent machinery and reports task success,
  verified completion, plan and repair attempts, approvals, call and byte
  proxies, unnecessary mutation and repeated-action stops.
- **SQLite scenario driver** (`sqlite_scenario_driver.rb`) — drives scenarios
  against the durable SQLite store: convergence probes, selector control,
  trace recording and manifest verification, all in clean subprocesses.
- **Memory treatment** (`memory_treatment_profile.rb`) — evaluates the memory
  system (episode corpus, retrieval, holdout) and reports attribution.

The scorecard applies three **hard-zero gates** — any violation fails the run
regardless of the other numbers:

- `no_unsafe_or_bypassed_actions` — zero unsafe or unauthorized actions;
- `no_false_positive_completions` — zero completions claimed without evidence;
- `complete_case_evidence` — zero cases with incomplete evidence.

The **rule-proposal scorecard** (`rule_proposal_scorecard.rb`) grades one
step of the episode worker on its own, `DraftPlaybookRule`: given verified cases
of one key, propose a condition that holds on the unseen cases of the key
(`must_hold`) and on none of the look-alikes, or decline with the right reason.
It checks its own discrimination first: an oracle drafter must win every case,
and a null, an always-true, an overfit and an always-decline drafter none. The cases are data in
`test/fixtures/domains/pump-station.json`. The tests drive it with a scripted
drafter (plumbing only). `script/rule_proposal_eval` runs it against a real model
and is never part of the test suite:

```bash
RUNS=5 AGENTEVAL_PROVIDER=zai AGENTEVAL_MODEL=glm-5.3-flash script/rule_proposal_eval > report.json
```

It needs the provider's key and a UTF-8 locale. One sample per case per run, no
confidence bound: it finds gaps, it does not certify the model.

## Release evidence artifacts

The audit documents live in the repository under `docs/` and are the
machine-readable release status:

| Artifact | What it is |
|---|---|
| `docs/requirements-manifest.json` | Generated from the invariants, the ADRs, the phase exit criteria, the public API, the CLI surface and the migrations |
| `docs/requirements-audit.json` | Regenerated by RUNNING each named test, so a row is `pass` only because its test executed and passed; carries the measured `release_blocking_gaps` |
| `docs/autonomy-scorecard.json` | The autonomy scorecard output, regenerated by `rake autonomy` |

## The gates

- `rake ci` — the everyday gate: design validation, syntax pass, the fast test
  set (slow and serial sets skipped, with a warning), the proto drift check and
  the architecture check.
- `rake ci_full` — the complete gate, nothing skipped: the full test set (fast,
  slow and serial) plus the same design validation, syntax, proto drift and
  architecture checks.
- `rake autonomy_strict` — the autonomy milestone gate: every scorecard case
  must pass.

## An honest note about the scorecard

The scorecard cases describe the product Tamoz is being built into. A case can
therefore fail until the product actually exists — the scorecard is a
**milestone gate** (it measures progress toward a described target), not a
**regression gate** (it does not merely check that nothing broke). Read a
failing case as "this described capability is not proven yet", and check the
[`../limitations.md`](../limitations.md) release-readiness section for the
measured state.
